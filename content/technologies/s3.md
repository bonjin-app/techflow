## TL;DR

S3 stores **objects** — arbitrary blobs with a string key and metadata — in buckets, and
serves them over [HTTPS](/concept/https). There is no file system, no directories (only
key prefixes), no appending and no in-place editing: you `PUT` a whole object and `GET`
it back. In exchange you get eleven-nines durability, near-unlimited capacity, per-GB
pricing and an API that has become the de-facto standard for object storage everywhere.
It is where files, media, backups, logs and data-lake tables live; it is not a database
and not a file share.

## Practical

Almost every backend touches S3 for something:

- **User uploads and media** — the browser uploads directly to S3 with a short-lived
  **presigned URL**, so the API server never proxies the bytes. A record in the
  database ([PostgreSQL](/technology/postgresql), [DynamoDB](/technology/dynamodb))
  stores the key and metadata.
- **Static hosting and delivery** — SPA bundles, images and video segments in S3
  behind a [CDN](/concept/cdn) that caches them at the edge.
- **Backups and logs** — database dumps, application logs, audit trails, with lifecycle
  rules moving old objects to colder, cheaper tiers.
- **Data lake** — Parquet/Iceberg tables queried in place by analytics engines.
- **Event source** — object-created notifications trigger thumbnailing, transcoding,
  virus scanning or indexing workers.

```ts
import { S3Client, PutObjectCommand } from "@aws-sdk/client-s3";
import { getSignedUrl } from "@aws-sdk/s3-request-presigner";

// API issues a 5-minute presigned PUT; the browser uploads straight to S3
export async function uploadUrl(userId: string, fileName: string, type: string) {
  const key = `uploads/${userId}/${crypto.randomUUID()}/${fileName}`;
  const url = await getSignedUrl(
    s3,
    new PutObjectCommand({ Bucket: "app-media", Key: key, ContentType: type }),
    { expiresIn: 300 },
  );
  return { url, key };          // store `key` in the DB once the client confirms
}
```

Operational habits: block public access at the account level and use presigned URLs or
a CDN origin access identity; enable versioning on anything you cannot re-create; tag
and lifecycle everything; name keys with high-entropy or date prefixes for easy
lifecycle rules.

## Deep Dive

**Consistency.** S3 provides strong read-after-write consistency for all operations:
after a successful `PUT`, every subsequent `GET` or `LIST` sees the new object. Earlier
eventual-consistency caveats no longer apply, which simplifies pipelines that write and
immediately list. See [Consistency](/concept/consistency).

**Durability versus availability.** Objects are redundantly stored across multiple
Availability Zones (except One Zone classes), giving the famous 99.999999999%
durability design target. Availability SLAs are lower (99.9–99.99% depending on class);
design for the occasional `503 SlowDown` or transient error with
[retries](/pattern/retry) and backoff. See [Availability](/concept/availability).

**Performance model.** Latency per request is tens of milliseconds — fine for large
objects, terrible for many tiny ones. Throughput scales with parallelism: multipart
uploads and ranged `GET`s, thousands of requests per second per prefix. S3 Express One
Zone is a separate single-AZ class with single-digit-millisecond latency for hot,
small-object workloads at higher cost.

**Storage classes and cost.** Standard, Intelligent-Tiering, Infrequent Access, Glacier
Instant/Flexible/Deep Archive trade retrieval latency and per-request cost against
per-GB price. Egress to the internet is the cost that surprises people; a CDN or
same-region compute keeps it down.

**Security model.** Access is IAM policies plus bucket policies plus (optionally) ACLs;
misconfigured public buckets are the classic cloud data leak. Server-side encryption is
on by default; object lock gives WORM retention for compliance.

**Not a file system.** No rename (copy + delete), no append, no partial overwrite, no
POSIX semantics. Tools that mount S3 as a drive work for reading, and mislead for
anything else.

## Why

Application servers are disposable and their disks are small, local and unshared. A
user uploading a profile photo to one server means the other servers cannot see it, the
disk fills up, and a redeploy wipes it. Serving large media through the application
consumes its threads and bandwidth on work that has nothing to do with business logic.

```sequence
title: Before — files on application server disks
participants: Browser, API-1 [nodejs], API-2 [nodejs]
Browser -> API-1: POST /upload (12 MB photo streamed through the app)
API-1 -> API-1: write /var/uploads/abc.jpg (local disk)
API-1 --> Browser: 201 Created
Browser -> API-2: GET /photos/abc.jpg (load balancer picked another server)
API-2 --> Browser: 404 Not Found ❌
API-1 -> API-1: disk 95% full; next deploy replaces the instance → files gone ❌
```

Moving objects to S3 gives every server (and the CDN) the same durable view, takes the
bytes off the application path entirely, and makes storage a per-GB bill instead of a
capacity-planning problem.

```sequence
title: After — direct upload to S3, delivery through a CDN
participants: Browser, API [nodejs], S3 [s3], CDN [cdn], Worker [backend]
Browser -> API: POST /uploads (metadata only)
API --> Browser: presigned PUT URL + key
Browser -> S3: PUT uploads/42/…/photo.jpg (bytes bypass the API)
S3 --> Browser: 200 OK (durable across 3 AZs)
S3 -> Worker: ObjectCreated event → generate thumbnails
Worker -> S3: PUT thumbnails/42/….jpg
Browser -> CDN: GET /thumbnails/42/….jpg
CDN -> S3: origin fetch (first time only)
CDN --> Browser: 200 OK (cached at the edge afterwards)
```

The same properties — cheap, durable, HTTP-addressable, event-emitting — make S3 the
landing zone for logs, backups and analytics data.

## Advantages

- Extremely high durability and effectively unlimited capacity with no provisioning
- Simple HTTP API that every language, tool and cloud-compatible provider supports
- Strong read-after-write consistency and versioning make pipelines predictable
- Storage classes and lifecycle rules tune cost from hot media to decade-long archives
- Presigned URLs and CDN integration keep large transfers off application servers
- Event notifications turn uploads into triggers for processing pipelines

## Trade-offs

- Per-request latency of tens of milliseconds; unsuitable for many small, hot objects without Express One Zone or a cache
- No append, rename or partial update — objects are immutable blobs
- Egress and request pricing can dominate cost for chatty or public workloads
- Flat namespace: listing millions of keys is slow and paginated; "directory" operations are client-side
- IAM/bucket-policy complexity makes accidental public exposure a real risk
- Availability is lower than durability; clients need retry logic and possibly multi-region replication

## When to use

- User-generated files, images, video, documents and other blobs referenced from a database
- Static asset and media origin behind a CDN
- Backups, snapshots, logs, audit trails and anything with retention rules
- Data lake and analytics storage in open table formats
- Decoupling producers and consumers of large payloads (upload once, many workers process)

## When not to use

- Don't use S3 as a database — key lookups, queries and small-record updates belong in [DynamoDB](/technology/dynamodb) or a relational store
- For low-latency hot data that changes frequently; use a cache such as [Redis](/technology/redis) or a block volume
- When you need POSIX file semantics (locks, appends, random writes) — use a network file system
- For millions of tiny objects that are read individually and constantly; request costs and latency add up
- As a message queue — object events are a trigger, not a broker; use [Kafka](/technology/kafka) or [RabbitMQ](/technology/rabbitmq)

## Real-world

In [Video Streaming](/architecture/video-streaming) S3 holds uploaded masters and the
transcoded HLS/DASH segments, which the CDN pulls from it as origin. An
[E-commerce](/architecture/e-commerce) platform keeps product images, invoices and export
files there with lifecycle rules for old orders. In [AI RAG](/architecture/ai-rag)
systems S3 is the document corpus: files land, an event triggers chunking and embedding,
and the vector index points back to object keys. A [Social Feed](/architecture/social-feed)
uploads media directly from the client via presigned URLs and stores only keys in the
feed items. Across all of them the pattern is the same: bytes in S3, metadata in a
database, delivery through a CDN.
